## Архитектура (MSX2 — база порта)

### Экран и темп
- SCREEN 5: 256×212, 16 цветов из 512, ОДНА палитра на всю игру (`test.plt` / `artwork/paleta.txt`).
- Игровое поле **256×160** = 16×10 «супертайлов» 16×16. Ниже — панель счёта до 192 строки.
- **Игровой тик = 5 кадров PAL (6 NTSC) → логика 10 Гц** (`frames_lock`, `waitforVBlank`). ZX-версия — те же 5 кадров. Это главный подарок для i8080: на тик ≈ 300К тактов.
- Главный цикл (`ianna.asm: mainloop`): пауза(H) → анимация тайлов (каждый 2-й тик) → `RunScripts` (скрипты всех 8 сущностей) → `CheckGravities` → `RedrawScreen_part1` (dirty-тайлы BG → спрайты → dirty-тайлы FG в теневую страницу) → `waitforVBlank` (5 кадров, в это время дорисовывается панель) → `RedrawScreen_part2` (показать страницу 1, скопировать dirty-прямоугольники в страницу 0 командой HMMM, показать страницу 0).

### Двойная буферизация
VRAM 128К: стр.0 — видимая, стр.1 — теневая (рисуем в неё), стр.2 — 256 тайлов уровня (сетка 16×16 тайлов по 16×16 px = 32К), стр.3 — шрифт/оружие/панель. Тайл рисуется VDP-командой HMMM (копия стр.2 → стр.1), спрайт — LMMC с прозрачностью (TIMP, цвет 0 прозрачен), зеркалирование — битом DIX в аргументе команды (зеркальные кадры НЕ хранятся).

### Тайлы (`tiles.asm`)
- Карта экрана: 160 Б BG + 160 Б FG (слой поверх спрайтов — для «глубины»; FG-тайл 0 = пусто) + 40 Б карта твёрдости (2 бита на супертайл, 4 значения) + 43 Б объекты = 403 Б, распакованы aPLib (`depack.asm`) в `CURRENT_SCREEN_MAP`.
- Тайлы ≥240 — анимированные (4 фазы в младших 2 битах, `AnimateSTiles`); список анимированных на экране собирается при загрузке (до 15).
- Dirty-rect: до 48 прямоугольников по 4 Б (xmin, ymin, nx, ny в супертайлах). `InvalidateTiles` (в чарах 8 px) → супертайлы. Перерисовка: BG dirty → все спрайты с флагом redraw → FG dirty.
- `GetHardness/SetHardness/SetStile/empty_supertile` — правка карты на лету (двери, ломающийся пол, ящики).

### Спрайты (`drawsprite.asm`, `sprite_*.asm`)
- Все спрайты **24×32**, 4bpp линейно (12 Б/строка, **384 Б/кадр**), 41 кадр = 16К-банк. Файл `sprite_*.asm` — DB-таблица, метки = анимации (idle, gira, camina, cae, agacha, saca_espada, idle_espada, camina_espada, espada_golpealto/adelante/comboadelante/bajo/atras, espada_ouch, muere). ВСЕ враги и варвар имеют одинаковый набор из 15 анимаций (одна и та же машина состояний!). Варвар: банк 2 общий + банк «доп.» (ouch, salta, salto_corto/largo, corre, frena, frena_gira, palanca, cuelga) + по банку на оружие (sword/eclipse/axe/blade = банки 3..6). Крупные враги (golem, ogro, minotauro, demonio) = 2 банка inf+sup (две сущности: главная + `OBJECT_ENEMY_SECONDARY`).
- Таблица спрайтов: 16 слотов × 8 Б (addr, type|ROM-bank, x, y, nchars_x, nchars_y, redraw). Позиция в пикселях, занятая площадь — в чарах 8×8. Клиппинг только по низу (y=160).
- `UpdateSprite` инвалидирует старую+новую площадь (объединяет по X при том же Y), `MarkOverlappingSprites` помечает перекрывающихся на перерисовку.

### Сущности и скрипты (`entities.asm` 4577 строк, `scripts.asm` 2258, `objects.asm` 773)
- 8 сущностей × 12 Б: игрок, 2 врага, 5 объектов. Байты: sprite ptr, script id, script pos, energy, state, anim pos, доп. индекс удара, последнее движение, номер в таблице объектов, тип|уровень врага.
- 66 состояний (STATE_* ×2 по направлению), таблица `player_state_functions` (33 функции). Prince-of-Persia-движение: бег/торможение/висение/лазание/длинный прыжок; бой: 4 удара + блок, вероятности по уровню врага (`enemy_info`, 32 Б на тип).
- Скриптовый байткод: 50 действий (`ACTION_*`), таблица скриптов ≤256 Б на экран + строки 2К на уровень; по 8 Б scratch на сущность (подскрипты).
- Таблица объектов уровня: 128 × 2 Б (state, props); чекпойнт = 512 Б (спрайты+сущности 224, статус 27, объекты 256).
- Уровни: заголовок 22 Б (offsets строк, nscreens, w, h, nscripts, nstrings, старт) + таблица адресов экранов + aPLib-экраны. 9 уровней (45–63 экранов, 6–12К) + level0 (attract, 8 экранов).

### Звук
Arkos Tracker 1 (`ArkosTrackerPlayer_CPC_MSX.asm`, ~1.9К кода, AY), музыка ≤4К + SFX 1.1К, в RAM по фиксированным адресам, ISR играет каждый кадр. 13 треков `.mus`.

### Раскладка ROM (43 банка ×16К = 688К)
0-1 код (32К Z80: движок+меню+интро+шрифты), 2-6 варвар, 7-21 враги, 22-39 уровни (карта+тайлы попарно), 40 музыка, 41-42 интро/финал, 43 attract+меню.

## Что подсмотреть у ZX-версии (лайфхаки)
1. **Зеркалирование через 256-байтную таблицу разворота байта** (`rotatetable.asm`) + перестановка колонок — зеркальные кадры не хранятся. На Векторе то же самое поплоскостно.
2. Спрайты **без масок, чистый OR** по фону (дизайн-док: «как в King's Valley», все движущиеся объекты одного атрибута). Для 16-цветной графики MSX2 маска нужна, но можно хранить одну маску на все 4 плоскости (уже делали в Metal Gear, −4.2К).
3. Тайлы 8×8 + супертайлы 2×2 + цвет на супертайл: тайлсет уровня 4К вместо 32К. Компромисс, если 32К тайлов в квазидиске окажутся тесны.
4. Теневой экран в RAM-банке 7 + копирование dirty-прямоугольников в реальный экран — та же схема, что MSX2, только процессором.
5. Слой ввода-вывода вынесен в `io-*.asm` (tape/+3DOS/esxdos/Dandanator/IF2) — готовый шов для нашего загрузчика EDD/FDD.
6. Карты памяти обеих версий — `src/memory_map.txt`, с точными размерами рантайм-структур.

## CPC-версия (бинарник)
Ближайший аналог нашей задачи: 16 цветов, без аппаратного блиттера, только CPU (Z80 4 МГц, mode 0 160×200). 32 банка: банк 0 — код (`di; ld sp,$bffe`), банки с заголовком `0f0f…` — графика. Дизассемблировать имеет смысл ТОЛЬКО ради ответа «как они делали двойную буферизацию/спрайты без VDP»; логику берём из MSX2.

## Куда идти на Векторе-06Ц (предложение)

Совпадения, которые делают порт естественным:
- Вектор: 256×256, 4 плоскости = 16 цветов из 256 (3-3-2). MSX2 SCREEN 5 арт ложится 1:1 (256 в ширину — ровно; 192 строки из 256; палитра 16 из 512 → 256 с потерей младшего бита синего).
- Спрайт 24×32 4bpp = 384 Б на MSX2 = 3 колонки × 32 Б × 4 плоскости = **384 Б на Векторе**. Тайл 16×16 = 128 Б там и там.
- Логика 10 Гц: ~300К тактов на тик. Оценка вывода за тик: спрайт с маской ≈ 96 Б×4 плоскости×~37 тактов ≈ 15К; супертайл pop-блитом ≈ 1.5К; 3 спрайта + 20 dirty-супертайлов ≈ 80К. Запас 3–4×.

Шов порта уже есть в исходнике: `vdp.asm` (1000 строк, все VDP-команды) + `sendSpriteGfx` + `depack/pletter` — платформенный слой; всё остальное (entities/scripts/objects/tiles-логика/ianna/input/score/menu) — переносится дословно ([[feedback_port_from_source_exactly]]).

Память (главная проблема, 64К минус 32К VRAM):
- Тайлы уровня 32К → **квазидиск**, pop-блит в стековом режиме прямо в VRAM (проверено в [[reference_vector06c_quasidisk]]: стековый доступ достаёт все 64К страницы, записи идут в основное ОЗУ).
- Спрайты (варвар 32–48К + враги уровня по 16–32К) → квазидиск, тот же стековый pop.
- Код: 32К Z80 в двух банках → на i8080 вырастет; резидент только движок, меню/интро/финал — кодовые оверлеи через окно $A000-$DFFF (в фазе, когда плоскости 1-2 не трогаем).
- Мелкие структуры ≤64 Б (сущности 96, спрайты 128, dirty 192, hardness 40, scratch 64…) можно класть в неиспользуемые 64 строки каждой колонки VRAM (8К кусками по 64 Б).
- Весь набор данных игры 688К > 256К квазидиска → полная игра требует подкачки с FDD на смене уровня; **первый рубеж — уровень 1 целиком в EDD** (тайлы 32К + карта 9К + варвар 32К + скелет/орк ~32К + музыка + код ≈ 120К).
- Звук: Arkos-плеер на IX/IY — проще снять PSG-дампы и играть psgVector-плеером (AY или ВИ53 на чистом 8080, см. [[reference_vector06c_fast_engine]]).

Вывод без второй страницы VRAM: у Вектора нет теневой страницы (32К VRAM = всё). Рисовать по dirty-rect прямо в экран за лучом (рецепт [[reference_vector_flicker_recipe]]); при 10 Гц на вывод есть целый кадр из пяти. Альтернатива — теневой буфер в квазидиске не годится (копия квазидиск→VRAM дороже прямой отрисовки).

Порядок работ:
1. Собрать MSX2 из исходников (pasmo/apack — поставить или собрать) → байт-в-байт с `ianna.rom` 1.2 → эталон для локстепа.
2. Конвертеры: тайлы/спрайты MSX2 4bpp → плоскости Вектора (+маска), палитра → порт 0C; уровни/скрипты — как есть (формат не меняем).
3. Векторный рантайм: pop-блит тайла из квазидиска, спрайт с маской и зеркалом, dirty-rect вывод за лучом, ISR (клавиатура+звук), загрузчик EDD.
4. Трансляция логики Z80→i8080 (IX/IY-сущности — см. [[reference_z80_to_i8080_recompilation]]), гейт локстепа против MSX2-эмулятора по game-RAM.
5. Уровень 1 в EDD на MiSTer, потом FDD-подкачка остальных уровней.

## Проверка эмулятора (2026-08-29)
`msx2_rom/ianna.rom` грузится в msx-emu MCP (`emu_load`), проходит `check_msx1` (BIOS $2D ≠ 0) и через 420 кадров крутится в halt-цепочке меню (PC=$911C). Поддержка V9938-команд (HMMM/LMMC, страницы VRAM) эмулятором ещё НЕ проверена — нужно снять VRAM и сверить с скриншотом.

## Сборка MSX2 из исходников — ✅ 2026-08-29
`./build.sh` → `build/msx2/ianna.rom` (720896 Б). Инструменты в `tools/bin`: pasmo 0.5.5 (собран из зеркала mkoloberdin/pasmo@stable, нужен `-std=c++14`), `apack` = обёртка над apultra (открытый упаковщик в формат aPLib), fill16k из репо.
Сверка с релизом v1.2: **42 из 44 банков байт-в-байт**; отличаются банк 40 (музыка — другой упаковщик) и 24 байта таблицы адресов музыки в банке 0. В headless WebMSX (`tools/msxemu/run_ianna.js`, машина MSX2+, формат ASCII16 — ОБЯЗАТЕЛЬНО передавать 7-м аргументом `loadFromContent`, иначе автодетект берёт ASCII8 и игра не стартует) на кадре 600 VRAM 128К и переменные игры идентичны релизу. Свободно в 32К кода: 1255 Б (`END_CODE=$BB19`).
`tools/msxemu/vram2png.py` — дамп VRAM SCREEN 5 → PNG.

## ✅ Тест движка на Векторе — 2026-08-29 (вечер)
Первый экран уровня 1 полностью рисуется, варвар ходит влево/вправо с анимацией, разворотом
(зеркало) и восстановлением фона; анимированная вода (FG-тайлы 244-247) — через штатный
dirty-rect механизм. Работает и в headless (`tools/run_vec.py`), и в vector06js.

Как сделано (движок — буквально из MSX2-исходника):
- `tools/z80to8080.py`: source-level трансляция pasmo-Z80 → i8080 (в Z80-мнемониках для
  `zasm --8080`). IX/IY в ячейках `z_ix/z_iy`, доступ через хелперы `src/vec/z80rt.asm`
  (`ld a,(ix+d)` = `ld a,d; call z_ix_rda` ~125 тактов; остальное — `call z_ix_xx; db d`).
  bit/set/res/djnz/ldir/exx/ex af/sbc hl — inline; анализ живости A и ОТДЕЛЬНЫХ флагов
  (с проходом по целям переходов) убирает лишние сохранения и печатает `!!FLAGS` там, где
  перевод неточен и флаги живы. Ручные правки — `tools/overrides.py` (сейчас только 2 места
  в депакере: `rl c`/`rr c`, где Z80-код читает Z после сдвига).
- Переводятся целиком: tiles, drawsprite, entities, scripts, objects, depack + нарезка
  ianna.asm (game/mainloop/LoadLevel/LoadScreen/RunScripts/...) + vars. Заменён только
  `vdp.asm` → `src/vec/vec_vdp.asm`; music/score/font/menu — заглушки (`vec_stubs.asm`).
- Отличие главного цикла: на Векторе `waitforVBlank` идёт ДО `RedrawScreen_part1` (нет
  теневой страницы — рисуем в начале кадра прямо в экран), `part2` только обнуляет dirty.
- Данные в квазидиске (`tools/data/build_edd.py`): стр.0 = кадры варвара банк 2 (768 Б/кадр:
  4 плоскости × 3 колонки × 32 строки × [data,mask], снизу вверх) + тайлы фона по $8000
  (128 Б, сверху вниз); стр.1 = банк 3 + FG-тайлы с маской по $6000 (LUT в ROM) + level1.map
  по $8000 (адреса внутри карты абсолютные от $8000 → окно квазидиска $8000-$DFFF на время
  LoadLevel/LoadScreen). Адрес кадра MSX ($8000+n*384) → физический = адрес*2 (=n*768) — без LUT.
- `setROM2` эмулирует страницы: 1 = закрыть окна, 2..21 = банк спрайтов, 22.. чётные = окно карты.
- ROM 26112 Б ($0100-$6700), 1 уровень: 5 кадров/тик как в оригинале (10 Гц).

Грабли, найденные по дороге:
- zasm: порядок аргументов `zasm src lst bin`, `-uwy` для таблицы меток; операнд `and (1<<4)`
  читается как косвенная адресация → маски числами.
- vector06js: имя ROM не может начинаться с `i` (префикс режима `i:`); синтетические клавиши
  нужны с полем `which` (`document.onkeydown({keyCode,which})`); чтение клавиатуры требует
  ППИ-порт B во ВХОД (`out(0),$82`), после — обратно `$80` + восстановить порт 2=0 и порт 3=$FF
  (mode set сбрасывает защёлки; порт 3 = ещё и скролл).
- MCP msx-emu (WebMSX) для Ianna не годится: MSX1 и без подсказки формата — свой харнесс
  `tools/msxemu/run_ianna.js` (MSX2+, ASCII16).

Что дальше: флаги `!!FLAGS` пересмотреть после расширения (сейчас 13 мест, все проверены
руками); панель счёта (score.asm) и шрифт; враги (скелет/орк) — банки в страницы 2-3;
звук (PSG-дампы); переход между экранами уже переведён (ChangeScreen) — проверить на краю
экрана; фликер оценить в живом браузере/MiSTer.

## ✅ Одиночный демо-ROM без квазидиска — 2026-08-29 (поздно вечером)
`python3 tools/data/build_edd.py --demo && python3 tools/build_vec.py --demo` → `build/ianna_demo.rom`
(32 512 Б, образ ровно до $8000; загрузка по $0100: vector06js `?sworddemo.rom`, MiSTer `.rom`,
Emu80 `--platform vector --run ianna_demo.rom`). Тот же движок, тот же код — отличается только
источник данных (`DEMO equ 1` в vec_vdp: ROM вместо страниц квазидиска).
Что влезло: 30 тайлов фона сцены + LUT (страница!), 4 передних тайла, 10 кадров варвара
(idle, поворот, ходьба×6, падение×2 — бег/прыжки дадут мусорный кадр), мини-уровень 285 Б
(45 ячеек карты → один экран, скрипты только игрока и кувшина), таблиц врагов нет.
Что пришлось сделать для бюджета (и это осталось в обеих сборках):
- спрайты 384 Б/кадр как в MSX2 (4 плоскости по строке), маска ~(p0|p1|p2|p3) на лету,
  блиты циклом; квазидиск: банк 2 = 15.7К вместо 31.5К;
- vars наверху ОЗУ (`org $6C00` / демо `$7400`), string_area фиксирована — **указатели в
  блоке строк/скриптов уровня абсолютные под $C000** (раньше скрипты читались из VRAM и
  «работали» случайно), `level_tools.py` перестраивает карту; **OBJECT_DATA обязана быть на
  границе страницы** (`ld h,OBJECT_DATA/256`) — было сломано;
- z80rt только используемые хелперы (подметки — вместе с родителем!), VDP-буферы/палитры
  убраны, string_area 1536 (демо 512).
Стартовое сообщение уровня (`ACTION_STRING` → `wait_till_read`) ждёт «огонь» — панели нет,
текст не виден: нажать Z/пробел, потом стрелки. run_vec.py: прерывание по бюджету
инструкций (иначе busy-loop ожидания никогда не видит клавиш).

## ✅ «Музыка замедляется при беге» — потеря кадровых прерываний под DI — 2026-08-30
Симптом: темп музыки плавает при движении героя (и, как выяснилось, стоя тоже — враги анимируются).
Причина: на Векторе прерывание от кадра НЕ защёлкивается — если в момент обратного хода стоит DI
(стековые блиты тайлов/спрайтов, сброс пула), запрос теряется (RTL MiSTer сбрасывает int при inte=0,
Emu80 так же; vector06js держит запрос — там дефект не виден). Каждый 5-й кадр — игровой тик с
блитами → ISR (и плеер Arkos) вызывался ~40 Гц вместо 50: старая сборка в Emu80 — стоя 39.3, бег 39.7/41.8 Гц.
Решение (`vec_budget`, vec_vdp.asm): ВИ53 как секундомер — не для звука. `vec_main` ставит счётчик 0
в режим 0 (выход низкий, на динамик ничего не идёт), ISR перезаряжает его $FFFF, перед каждым
блитом `vec_budget` защёлкивает счётчик (out $08←0, in $0B ×2), считает прошедшие тики от VBlank
(1.5 МГц = 2 такта CPU), и если «прошло + стоимость блита» > 27000 тиков (кадр ~29950) — `halt` до
следующего прерывания, только потом `di`. Стоимости: тайл 9, FG-тайл 11, спрайт 105 (×256 тактов),
слот пула 9. Без таймера (headless emu_kvaz) порт читается $FF → «0 тиков» — бюджет молчит.
Результат в Emu80: экран сообщения 49.9, стоя 50.7, бег 24 с туда-сюда 49.6 Гц; `halt` бюджета
4–15/с (блиты тика ложатся на 2 кадра из 5). Побочный дефект при внедрении — в `vec_pool_flush`
вызов бюджета затирал A (номер слота) перед `vec_pool_addr`: мусор в тайлах и пропавший герой; починено.
Замер: `tools/emu80_measure.py` (перезапуск Emu80, Z, бег; выборка cpu_ticks/FrameCounter/vec_bud_halts
под `debug_break`; cpu_ticks Emu80 идут на 3.125 МГц — 62592 тактов/кадр).

терялось ~24 % кадров, музыка подвисала, кредиты мигали. Замечено: **валик — строго горизонтальные полосы**
(каждая его строка одного цвета, проверено по `menu_screen.SR5`). Поэтому фон под пунктами теперь не копируется, а
заливается константами (`mb_stripes`, таблица 4×32 байта генерируется в `build/menu_stripes.asm`): ни чтения
квазидиска, ни DI. Замер в Emu80: 4 смены пункта — 173 кадра из 173, потерь нет. Копия в квазидиске осталась только
для нижней строки (слот 1, 1024 Б) — она меняется раз в ~5 секунд.

Ловушки, пойманные здесь:
- таблица полос лежит в оверлее, то есть **видна только при открытом окне** — её нужно скопировать в ОЗУ до того,
  как окно закроется (иначе читаются пиксели VRAM);

Экран пароля: приглашение укорочено до «ПАРОЛЬ:»/«PASSWORD:», строка ввода идёт сразу за ним (18 знаков с колонки 7 —
по центру), пункты меню при этом не стираются, после ответа возвращаются кредиты. Раньше пустой валик и сообщение
«INVALID PASSWORD» выглядели как зависание — игра просто ждала огонь.

Волна: сдвиг переписан на одно чтение на байт (идём с той стороны, где сосед уже прочитан).

### Нижняя строка — как в оригинале (2026-09-01)
Оригинал печатает нижнюю строку (титры, приглашение и поле пароля, ответы) НЕПРОЗРАЧНО: `print_string3` →
`drawCharFront`, то есть с фоном шрифта, а очищает её печатью 32 пробелов (`menu_cleancreditsattr`, строка 23,
колонка 0). Прозрачная печать (`drawCharTrans`) в оригинале только у пунктов меню и меню паузы. У нас нижняя строка
шла прозрачной — отсюда ощущение «не влезает / наезжает на картинку». Теперь: `ovl_printf` (непрозрачно, через
`drawChar` движка) + очистка пробелами вместо копии фона из квазидиска; слот 1 копии больше не нужен.
Титры остаются одной строкой с ротацией трёх записей — в оригинале ровно так (три `string_credits`, все в строке 23).

Ловушка: строки 20..23 — область панели, и `drawChar` держит для неё кэш «по изменению», поэтому повторная печать
молча пропускалась (строка оставалась пустой). Перед печатью нижней строки сбрасываем кэш (`vec_pc_reset`).

### Нижняя строка: точечная очистка и ввод без дёрганья (2026-09-01)
Очистка всей строки 23 пробелами (как `menu_cleancreditsattr`) закрашивала чёрным всю ширину экрана. Теперь `ovl_printf`
запоминает x и длину напечатанного (только на входе — не на каждом символе, иначе запоминается последний знак), а
`ovl_clr19` затирает ровно эту область. Плашка остаётся только под текстом, картинка по бокам цела.

Дёрганье экрана при вводе пароля: сканирование клавиатуры трогает порт `$03`, а это ещё и регистр вертикального
скролла — делать это посреди кадра нельзя. Сканер (`mb_key` в блобе) теперь вызывается ИЗ ISR через хук
`vec_key_hook` (в VBlank, там же, где `get_joystick`), результат кладётся в `vec_key`; оверлей только читает ячейку и
включает/выключает хук на входе и выходе экрана пароля. Замер: ввод 6 знаков — 127 кадров из 127.

### Титры и волна — по оригиналу (2026-09-01, вечер)
**Титры**: в оригинале три записи ровно по 16 знаков (`"  CODE: UTOPIAN "`, `"ART: PAGANTIPACO"`, `"  SOUND: MCALBY "`),
печатаются с фиксированной колонки 8 и **затирают друг друга сами** — отдельной очистки при ротации нет.
`menu_cleancreditsattr` (32 пробела) вызывается только перед сообщениями пароля. Мы очищали строку при каждой ротации,
из-за чего чёрная плашка шла во всю ширину. Теперь как в оригинале: строки с пробелами, колонка 8, без очистки;
полная очистка осталась только у экрана пароля. Первый титр печатается сразу при входе в меню (у оригинала первый
`credit_timer` = 0, у нас он появлялся через 256 кадров).

**Волна**: край строки, откуда «приходит» пиксель, больше не затирается — крайний байт только читается, запись идёт
с соседнего. Раньше он заполнялся нулями, и края полосы отражения были рваными; в оригинале VDP-копия край не трогает,
поэтому границы плоские. Заодно оба направления сдвига переписаны на одно чтение на байт (исходный сосед держится
в регистре).

**Волна, окончательно**: сдвиг сделан ЦИКЛИЧЕСКИМ — бит, уходящий за край строки, приходит с другой стороны.
Сдвиг с потерей (даже с нетронутым крайним байтом) дублирует краевой пиксель, и за десяток проходов узор отражения
вырождается в сплошные полосы; при циклическом сдвиге информация не теряется вовсе, картинка живёт бесконечно.

**Волна, скорость**: внутренний цикл сдвига переписан — адрес держится в HL и двигается шагом 256 (`inc`/`dec H`),
перенос между байтами идёт через флаг (`rlca` соседа + `rla` байта). Было ~90 тактов на байт, стало ~45.
Это и была причина «проблескивания»: 8 строк × 4 плоскости × 32 байта = 1024 байта по 90 тактов ≈ 92К тактов,
то есть БОЛЬШЕ кадра (60К) — луч заставал полосу недорисованной. Теперь ≈46К, укладываемся в кадр,
счётчик кадров в меню — 201 за 4 с (ровно 50 Гц).

## 2026-09-01 — загрузчик уровней: задел (в работе)

**Ёмкость решена сжатием.** Набор уровня (256 КБ квазидиска) жмётся aPLib блоками по 8 КБ втрое:
уровень 1 — 78.9 КБ, уровень 2 — 64.4 КБ. Значит все девять уровней (~650 КБ) помещаются на дискету 800 КБ,
тогда как сырых образов туда влезает ровно один. Инструмент: `tools/build_levels.py` — гоняет `build_edd --level=N`,
режет на 32 блока, пакует, кладёт в `build/levels/levelN.pak` (формат: 32 слова длин, затем блоки; длина 0 = блок нулевой).

**Раскладка дискеты под уровни** (черновик, в `build_fdd.py` пока не влит): дорожка 4 — каталог (16 записей
по 4 байта: дорожка, сектор, длина в секторах), дорожки 5..39 и 64..79 — сжатые наборы, меню и слайды на своих местах.

**Загрузчик** (`vec_fdd.asm`, 439 Б в области rev256/slot_tab): читает каталог, открывает поток с дорожки уровня,
для каждого блока читает сжатые данные в VRAM `$8000`, распаковывает готовым `depack` в VRAM `$C000` и копирует
8 КБ в квазидиск стековым режимом. Экран в это время не нужен, поэтому VRAM используется как буфер.

**Что уже проверено на стенде:** каталог читается верно (дорожка 5, сектор 1 для уровня 1) — то есть позиционирование
и первое чтение работают. **Что не работает:** чтение потока после перехода на дорожку уровня возвращает пустые
данные, распаковщик получает мусор и зацикливается. Найденные по дороге причины (исправлены): `current_level`
читался до его инициализации в `vec_start`; цикл чтения сектора «по флагам DRQ» (трюк ПЗУ) при неснятом DRQ крутится,
пока адрес не переполнится, затирая память — заменён явным счётчиком на 1024 байта; пошаговое позиционирование
заменено командой SEEK. Осталось разобраться, почему второе чтение не наполняет буфер.

**ВАЖНАЯ находка по сборке:** в `vec_vars.asm` лежала КОПИЯ `vec_fdd.asm`, а не включение — правки в файле молча
не попадали в ROM. Теперь там маркер `; @@INCLUDE vec_fdd.asm`, а тело подставляет `build_vec`.

До завершения загрузчика в дереве оставлена рабочая схема: сырой образ уровня 1 на дорожке 4 (как раньше).

### Идея на потом: вода и огонь «одним байтом в N колонок»
Профиль стартового экрана: `drawTile` 477 вызовов за тик, `drawFGTile` 189, блиттер — 60 % тика. Анимация уже
собирает соседние тайлы одной строки в серию (`vec_an_run`), тайл рисуется стековым блитом без чтения фона.
Кадры воды и огня — самостоятельные рисунки, не сдвиги друг друга (проверено по `tiles_nivel01.SR5`), поэтому
трюк волны из меню тут не применим. Но в серии тайлы ОДИНАКОВЫЕ, а колонки VRAM идут с шагом 256 — значит байт
кадра можно писать сразу в N соседних колонок (`ld (de),a` + `inc d`), ~12 тактов на байт вместо ~21 у стекового
блита, почти вдвое. Серии у нас уже вычисляются, так что нужен только быстрый путь «серия одинаковых тайлов».

### Загрузчик уровней: чтение работает, запись в квазидиск — нет (2026-09-01, продолжение)
Схема упрощена: дорожку начала набора **прошиваем прямо в ROM** (таблица `vfl_dirtab`, её пишет `build_fdd_pack.py`
по адресу из листинга), поэтому позиционирование ровно одно — RESTORE плюс шаги, как в рабочем чтении экрана меню.
Каталог с дискеты больше не читается.

Найденные и исправленные ошибки:
1. `vfl_byte` держал указатель потока в `HL` — а вызывающий держал там адрес назначения. Каждый прочитанный байт
   ломал адрес, поток «съедался» по паре байт на сектор, и головка уезжала по дорожкам. Теперь `HL` сохраняется.
2. Чтение сектора «по флагам DRQ» (трюк ПЗУ) при неснятом DRQ крутится, пока адрес не переполнится, затирая память —
   заменено явным счётчиком 1024 байта.
3. `current_level` читался до инициализации в `vec_start` — индекс уровня был случайным.

Сейчас: набор читается и распаковывается целиком, маркер `'IA'` в конце пишется. **Осталась ошибка записи в
квазидиск**: данные ложатся со смещением — фрагмент, лежащий в странице 0 по `$D000` (это позиция блока 6),
найден в эталоне на странице 2 по `$C680` (блок 22, плюс сдвиг `$980`). Смотреть надо `vfl_store` (перенос 8 КБ
из VRAM в квазидиск стековым режимом) и фактическую длину распаковки блока.

Чтобы дерево оставалось рабочим, задел лежит отдельно: `src/vec/vec_fdd_pack.asm` и `tools/build_fdd_pack.py`;
в сборке — прежняя схема с сырым образом уровня 1.

## 2026-09-01 — почему музыка в игре звучала неправильно

Симптом: после меню и интро мелодия уровня звучала «не так». Проверка потока регистров AY показала: данные песни
в квазидиске корректны, плеер сам по себе идеален (гейт `tests/music/check.sh` — 600 и 6200 кадров без расхождений),
а вот в игре после фазы меню поток отличался — **ровно по трём регистрам: 6 (период шума), 11 и 12 (огибающая)**.

Причина: плеер Arkos каждый кадр выводит все 14 регистров из своих теневых ячеек (`_atVAR_Reg6/11/12`).
Песни меню и интро шум и огибающую задают, песня уровня — нет, поэтому в ячейках оставались последние значения
от интро (13, 181, 1) и звучали поверх мелодии уровня всё время игры.

Что не помогло и почему: сброс в `ovl_go` (при выходе из меню) бесполезен — до загрузки песни уровня плеер ещё
доигрывает интро и снова пишет туда свои значения; `MUSIC_Stop` глушит только громкости; `MUSIC_Init` эти ячейки
не трогает. Рабочее место сброса — сразу ПОСЛЕ `MUSIC_Load` в `game()`, это и сделано (вставка в нарезку `ianna.asm`).

Проверка: поток AY в игре после меню теперь совпадает с потоком в игре без фазы меню — 238 из 239 кадров,
расхождений по регистрам ноль.

Методическая заметка: короткая сверка «первые 64 байта песни» ничего не значит — у всех песен одинаковый заголовок
(`AT10...`), из-за чего проверка ложно проходила. Сверять надо весь файл и сам поток AY.

### Загрузчик уровней: загрузка проходит целиком, но блоки ложатся не на свои места (2026-09-01)
Прогон в Emu80: 32 блока читаются и распаковываются примерно за 30 секунд (≈1 блок/с), маркер `'IA'` выставляется,
управление возвращается в игру. То есть чтение потока, распаковка и завершение цикла работают.

Сверка квазидиска с эталонным EDD (через окно `$A000-$DFFF`, доступны блоки 5..7 каждой страницы): совпало 5 проб
из 16. Найденные несоответствия — не сдвиг на постоянную величину, а перепутанные позиции:
`стр.1 $C000` содержит данные блока 0, `стр.1 $D000` — блока 9, `стр.3 $D000` — блока 22.

Арифметика в `vfl_store` на бумаге сходится (блок i → страница i/8, старший байт смещения `(i&7)*32`, SP = конец
блока, push вниз), значит ошибка либо в стековой записи (порт/страница на момент push), либо в том, что `depack`
выдаёт не ровно 8192 байта и хвост тянется из предыдущего блока. Следующий шаг — изолированный тест `vfl_store`:
записать в каждый блок известный узор и прочитать обратно, не привлекая дискету и распаковку.

Начало страниц (`$0000-$7FFF`) через окна не читается, поэтому для проверки нужен либо стековый режим, либо узор,
попадающий в доступные окна.

### ЗАГРУЗЧИК УРОВНЕЙ РАБОТАЕТ (2026-09-01)
Набор уровня грузится с дискеты СЖАТЫМ и распаковывается в квазидиск. Проверено в Emu80 end-to-end:
меню → интро → игра на уровне 1, собранном из `level1.pak`; сверка квазидиска с эталонным EDD — 18 проб из 20
(два расхождения в странице 3 по `$B000` и `$C980`, где игра сама держит копию фона меню и активную песню).

Что оказалось причиной долгих поисков: изолированный тест записи блоков (в каждый блок — его номер) показал, что
`vfl_store` **работает идеально** — все 12 проверенных позиций верны. Ошибка была не в коде, а в сборке: образ
собирался прежним `build_fdd.py` (сырой EDD на дорожке 4), а ROM — новым загрузчиком, который читал эти байты как
сжатый поток. Отсюда «блоки не на своих местах». После сборки образа правильным сборщиком всё сошлось.

Итоговая схема: `tools/build_levels.py` собирает `build/levels/level{N}.pak` (32 блока по 8 КБ, aPLib),
`tools/build_fdd.py` раскладывает наборы по дорожкам (4..39 и 64..79) и **прошивает таблицу дорожек прямо в ROM**
(`vfl_dirtab`), `src/vec/vec_fdd.asm` при старте читает набор для `current_level`, распаковывает блок в VRAM `$C000`
и переносит в квазидиск стековым режимом. Загрузка уровня 1 (79 КБ сжатых) занимает около 30 секунд —
чтение потока идёт побайтно через вызов, это первый кандидат на ускорение.

### Индикатор загрузки уровня
Загрузка набора занимает около 30 секунд, поэтому в загрузчик добавлена полоса прогресса: одна колонка на блок,
32 колонки на всю ширину. Тонкости, которые пришлось учесть:
- шрифта при ПЕРВОЙ загрузке ещё нет (он приезжает вместе с набором), поэтому текстовой надписи там быть не может —
  только графика; текст можно будет добавить для смены уровня уже в игре, когда шрифт лежит в квазидиске;
- VRAM на время загрузки служит буфером (сжатый блок в `$8000`, распаковка в `$C000`), поэтому экран гасим палитрой:
  все цвета чёрные, кроме цвета 1, а полосу рисуем в плоскости младшего бита (`$E000-$FFFF`) — её загрузка не трогает;
- палитра Вектора защёлкивается только в кадровом гасящем, а при старте прерывания запрещены и фаза луча неизвестна,
  поэтому палитру пишем заново на каждом блоке — какая-то из записей попадает в нужный момент.

### Ловушка: ROM и набор уровня обязаны собираться парой
Симптом: герой в прыжке рисовался скелетом. Причина не в спрайтах и не в загрузчике — `build_edd.py`
уровнезависим и попутно генерирует `gen_data.asm` (палитра, **таблица банков** `vec_bank_tab`, LUT передних тайлов),
которая вкомпилируется в ROM. Я гонял `build_edd --level=2` для замеров сжатия, `gen_data` остался от уровня 2,
и ROM стал считать, что прыжковый банк героя лежит по адресу, где в наборе уровня 1 лежит скелет.

Сделано, чтобы не повторилось: `build_levels.py` после цикла по уровням восстанавливает `gen_data.asm` и
`build/ianna.edd` для уровня 1 (он же гоняет `build_edd` для каждого уровня и портит их); `build_vec.py`
предупреждает, если `ianna.edd` новее `gen_data.asm`.

Правильное решение на будущее (нужно для смены уровней в игре): вынести уровнезависимые таблицы из ROM в набор —
класть их в квазидиск и копировать в ОЗУ при старте уровня. Тогда ROM станет универсальным, а рассинхрон
станет невозможен в принципе.

## Темп анимации воды и огня

Вода и огонь анимируются вдвое реже оригинала: каждый 4-й тик вместо каждого 2-го (`and 3` вместо
`and 1` у счётчика `animate_tile` в mainloop). Причина — блит анимированных тайлов заметно дороже
всего остального в тике: на уровне 1, экран 4,0 (девять анимированных супертайлов) тик из-за него
растягивался до 10 кадров при номинале 5, и анимация шла рывками через раз.

**Замер (headless, 300 кадров без ввода):**

| экран | анимтайлов | оригинальный темп | каждый 4-й тик |
|---|---|---|---|
| ур.1 (0,0) | 2 | 9.8 тик/с, тиков >5 кадров 24 % | 9.8 тик/с, 17 % |
| ур.1 (4,0) | 9 | 9.2 тик/с, 49 %, простой 36 % | 9.5 тик/с, 25 %, простой 56 % |
| ур.1 (4,1) | 10 | 10.1 тик/с, 49 %, простой 49 % | 10.0 тик/с, 25 %, простой 64 % |
| ур.1 (0,6) | 6 + две мумии | 7.3 тик/с, 81 % | 8.0 тик/с, 66 % |
| ур.2 (4,6) | 2 + голем | 8.4 кадра/тик | без изменений — там платит блит спрайта |

`IANNA_ANIM_MASK=1 python3 tools/build_vec.py` собирает образ с оригинальным темпом для сравнения.

Сначала это было сделано адаптивно (модуль `vec_anim.asm`: замедление включалось только там, где
экран не тянет номинальный темп, по накопленному долгу в кадрах — коммит d6d5730). Механизм работал,
но выигрыш давал тот же, а стоил 40 байт кода, двух ячеек ОЗУ и отдельного инструмента отладки,
поэтому заменён на постоянную маску. Если понадобится вернуть — вся логика и разбор ловушек в том
коммите.

**Ловушка размещения, из-за которой адаптивный вариант не помещался.** Вставка 45 байт в mainloop
роняла сборку наездом кода на переменные, хотя запас был 101 байт: в gen_data перед `fg_tile_lut`
стоит выравнивание на страницу `ds ($+255)&$FF00-$`, и запаса до границы там всего 34 байта — всё,
что добавлено ВЫШЕ, толкает LUT и весь хвост образа на целую страницу (+256 Б).

**Вторая ловушка:** патч mainloop накладывается на уже транслированный `ianna_main.asm`. Если
вставлять в `ianna_main_src.asm` (до трансляции Z80→i8080), транслятор считает соседние инструкции
нуждающимися в сохранении флагов и тянет лишние хелперы `z_*`.

## Порядок сборки дискеты (иначе игра срывается после загрузки)

Оверлеи меню и паузы живут в КВАЗИДИСКЕ — то есть внутри набора уровня (`build/levels/level{N}.pak`),
а функции движка зовут по адресам той сборки ROM, при которой собраны. Пересобрать ROM и не пересобрать
наборы — значит положить в квазидиск меню от прежней сборки: после загрузки уровня экран остаётся
чёрным, `FrameCounter` замирает, PC гуляет по случайным адресам. Сборка ROM+EDD при этом работает,
потому что EDD пересобирается заодно с оверлеями — ломается только дискетная.

Правильный порядок:

```
python3 tools/build_vec.py      # ROM и оверлеи
python3 tools/build_levels.py   # наборы уровней со СВЕЖИМИ оверлеями (заодно чинит gen_data на уровень 1)
python3 tools/build_vec.py      # ROM ещё раз, если gen_data изменился
python3 tools/build_fdd.py      # образ дискеты
```

`build_levels.py` пишет рядом с набором отпечаток оверлеев (`level{N}.ovl`), а `build_fdd.py` сверяет
его с текущими `build/*.bin` и отказывается собирать образ при расхождении, называя порядок сборки.

## Перестановка номеров цветов: мумия в младших восьми (COLOR_SWAPS)

Чтобы спрайт не занимал четвёртую плоскость, все его цвета должны иметь номера меньше восьми.
У мумии шесть красок — 1 чёрный (35 % точек), 7 тёмно-серый (22 %), 6 белый (21 %), 11 бежевый (20 %),
3 красный (2 %, повязка и кровь), 13 зелёный (0.2 %, глаза); мешают только 11 и 13.

Свободных младших номеров на её экранах нет — фон занимает все 1..7. Но свободные и не нужны:
номера меняются МЕСТАМИ вместе с регистрами палитры (`COLOR_SWAPS = [(11,5), (13,2)]` в build_edd),
цвета остаются на своих местах, картинка не меняется ни на точку. Проверено: кадры экранов (4,5),
(0,6), (4,0) до и после перестановки совпадают побайтно. После неё мумия красится в {1,2,3,5,6,7},
жёлтые блики платформ ездят под номером 11, бежевый героя — под номером 5; четырёхплоскостным
спрайтам номера безразличны. Зашитые в коде цвета (1, 4, 10 — заливка панели и шкалы) не затронуты.

`IANNA_NOPERM=1 python3 tools/data/build_edd.py` собирает данные без перестановки.

**Сколько это даёт.** Замер на экранах уровня 1 (300 кадров):

| вариант | 4,5 | 1,5 | что не так |
|---|---|---|---|
| как есть, 4 плоскости | 8.3 тик/с | 7.9 тик/с | — |
| плоскость 3 только чистится маской (`IANNA_SPR3CLR=1`) | 8.4 | 8.0 | законно, но экономит одну команду `or` из шести на строку |
| плоскость 3 не трогается вовсе (`IANNA_SPR3=1`) | 8.7 | 8.4 | под спрайтом остаются старшие биты фона — картинка неверна |

То есть законный трёхплоскостной спрайт даёт около процента: фон уровня использует старшую
плоскость (13 % точек), поэтому её под спрайтом всё равно приходится чистить, и экономится только
чтение данных. Четверть времени блита получилась бы, если бы плоскость 3 фона была нулевой —
это уже переход всей сцены на 8 цветов.

Что перестановка даёт наверняка — возможность хранить банк в трёх плоскостях: 96 Б на кадр,
3.9 КБ на банк (не реализовано, пригодится, когда наборы уровней перестанут влезать в квазидиск).

## Готовые зеркальные копии кадров (vec_mirr.asm, build_edd.MIRRORS)

Зеркальный блит разворачивает КАЖДЫЙ байт строки через таблицу rev256 заново на каждом тике и
стоит вшестеро дороже прямого: профиль экрана 4,5 (две мумии) — `dspm_row` 20.9 % тика против
`dsp_row` 3.4 %. Потолок, если зеркальный путь вообще убрать (`IANNA_NOMIRROR=1`, картинка неверна):
экран 4,5 идёт 10.0 тик/с вместо 8.3.

Кадр меняется почти каждый тик, но разных кадров в обороте 7..10 — цикл анимации повторяется,
поэтому копии готовятся заранее: отражаем пиксели и гоним через тот же конвертер, формат совпадает
с прямым кадром. `vec_mirror_src` подменяет адрес источника и сбрасывает признак зеркала — дальше
идёт обычный прямой блит. Проверено моделью: развёрнутые байты и переставленные колонки прямого
кадра совпадают с копией байт в байт для всех кадров.

**Три ловушки, каждая ловилась замером:**

1. **Страницу сверять обязательно.** Одни и те же адреса в другой странице принадлежат другому
   банку: камень лежит в стр.3 по $2800-$8440 и без проверки порта попадал бы в диапазон мумии.
2. **Стр.2 $E000-$EFFF занимать нельзя** — туда меню сохраняет песню уровня (`menu_ram.mb_savelvl`),
   и зеркала затирались в рантайме: мумия рисовалась цветным мусором. В образе EDD область при этом
   нулевая, так что проверка «занято ли» по образу ничего не ловит — нужен прогон.
3. **Зеркалить надо не первые кадры, а те, что рисуются зеркально.** У мумии ходьба вправо идёт
   кадрами 0..7, влево — 14..17 (замер `frame_stats`), поэтому диапазон задаётся как (первый, сколько).

Раскладка копий: мумия — стр.2 $F000, кадры 14..20; орк — стр.3 $F000, кадры 2..8 (в стр.2 места не
осталось, поэтому в записи таблицы есть отдельный порт страницы КОПИЙ); варвар — стр.0 $6900 и
стр.1 $5D00. Все четыре области проверены прогоном: в рантайме не затираются.

**Замер (300 кадров, экраны уровня 1):**

| экран | было | стало |
|---|---|---|
| 4,5 (две мумии) | 8.3 тик/с | 9.1 |
| 0,6 (две мумии) | 7.8 | 8.1 |
| 1,5 (два орка) | 7.9 | 8.6 |
| 0,5 (два орка) | 8.0 | 8.9 |
| 0,4 (орк) | 8.2 | 8.9 |

Это все пять экранов уровня 1, что шли медленнее 9 тик/с.

Сверка картинки: снимок после фиксированного числа ТИКОВ (`tools/shot_tick.py --fixrand`, иначе
сборки разной скорости расходятся по фазе анимации) совпадает с эталоном побайтно.
`IANNA_NOMIRRDATA=1` собирает данные без копий.

## Подёргивание экрана: опрос клавиатуры трогал регистр скролла

Порт $03 на Векторе — это и выбор ряда клавиатуры, и РЕГИСТР ВЕРТИКАЛЬНОГО СКРОЛЛА. `get_keyboard`
писал в него номер ряда и возвращал $FF, а звался каждый тик прямо из mainloop (проверка H — пауза),
то есть в произвольной фазе кадра: пока луч рисует, картинка уезжала на несколько строк. Внешне —
экран изредка «подёргивается».

Тот же камень уже ловился на экране ввода пароля и был закрыт хуком `vec_key_hook` (скан только в
ISR), но обычный игровой опрос остался прямым.

Теперь клавиши H/J/X сканируются в ISR, в кадровом гасящем, рядом с опросом джойстика: два ряда
($DF — H и J, $7F — X) складываются в маску `vec_keys`, а `get_keyboard` только читает её и портов
не трогает вовсе. Проверка: `tools/scroll_check.py` считает записи в порт $03 по функциям — все
записи идут из ISR (isr_nopal + get_joystick), из игрового кода ни одной.

Заодно `tools/run_vec.py` научился эмулировать ряд 5 клавиатуры (h, j), поэтому пауза проверяется
headless: нажатие H открывает фазу паузы.

## Освобождение ROM: LUT передних тайлов вместо 256 байт — дюжина пар

В ROM оставалось 14 свободных байт, и любая правка движка упиралась в это. Первый резерв нашёлся в
данных: `fg_tile_lut` занимал 256 байт (прямой доступ по номеру тайла), а занято в нём 12 записей —
столько передних тайлов на уровне. Заменено на список пар (номер тайла, индекс) с перебором:
`drawFGTile` зовётся около десяти раз за тик, дюжина сравнений там не видна.

Освободилось 252 байта (зазор до переменных 14 -> 266 Б): 256 байт таблицы плюс 30 байт выравнивания
на страницу минус 24 байта пар и 22 байта кода поиска. Замер не изменился: экран (4,1) с десятью
анимтайлами и девятью передними — 10.0 тик/с, (4,0) — 9.5, (4,5) — 9.0.

Побочная выгода: вместе с таблицей ушло выравнивание `ds ($+255)&$FF00-$`, из-за которого любые
40 байт, добавленные выше него, толкали весь хвост образа на +256 Б и роняли сборку наездом на
переменные — эта ловушка ловилась дважды (адаптивный темп анимации и подмена зеркальных кадров).

### Резерв мёртвого кода оказался мифом (проверено вырезанием)

Отдельный проход по таблице символов zasm (флаг `(unused)`) с отсечкой «проваливания» — метка годится
в кандидаты, только если перед ней стоит `ret`/`jp` — дал 35 меток на 1244 байта: entities.asm 649,
scripts.asm 271, score.asm 136, ianna_main.asm 69, vec_vdp.asm 48, прочее 71.

**Пользоваться списком напрямую нельзя** — две первые же выборочные проверки оказались ложными:

- `fillArea` (48 Б) — АЛИАС: `fillArea:` и `fillArea_slow:` стоят на одном адресе $6437, вызывается
  второе имя. По профилю эта функция отрабатывает 200 раз за тик.
- `vec_ovl_call` (25 Б) — вызывается из `pause_ovl.asm`, а тот собирается ОТДЕЛЬНО, как оверлей
  квазидиска: в основном образе ссылки нет, поэтому ассемблер честно пишет «unused».

Третий класс риска, который проверкой не отсечь: состояния сущностей могут адресоваться вычислением
(база + смещение), и тогда живой код тоже выглядит несосланным. Так что перед вырезанием каждого
куска нужно смотреть глазами, а результат сверять прогоном.

Скрипт разбора: `scratchpad/deadcode_scan.py`, дамп — `deadcode_report.json`.

## Таблицы уровня переехали из ROM в набор (условие смены уровней)

Палитра, таблица банков спрайтов и передние тайлы были константами в ROM. Из-за этого в игре можно
было жить только на том уровне, при котором собирали образ: набор менялся, а таблицы оставались
старыми, и движок читал спрайты по чужим адресам (ловилось как «герой в прыжке стал скелетом»).

Теперь `build_edd.level_table_blob` кладёт их в САМ НАБОР — стр.2 $BC40, хвост банка мумии, 81 байт:
16 байт палитры, 40 байт таблицы банков (порт стека страницы + старший байт базы), число передних
тайлов и пары (номер тайла, индекс). Адрес попадает в окно $A000-$DFFF, поэтому читается обычным
`ldir` без стековых плясок. В движке — `vec_load_leveltab` (~30 байт, вызывается при старте, под DI:
прерывание играет музыку из своего окна и сбило бы наше).

В ROM это ничего не стоило: таблицы просто стали переменными (зазор даже вырос до 301 Б, потому что
из образа ушли их константы).

**Ловушка, из-за которой экран позеленел.** Порядок сборки замкнут в кольцо: `build_edd` кладёт в
образ .bin оверлеев от предыдущего `build_vec`, а `build_vec` берёт из образа адреса. Без второго
прохода в образе остаётся оверлей от прежней сборки — он пишет по чужим адресам. Проявилось это
одним испорченным байтом: `ovl_light` восстанавливал палитру из своей копии и клал мусор в слот 5.
Раньше в слоте 5 сидел жёлтый (0.5 % точек), и никто не замечал; после перестановки цветов туда
переехал бежевый — и небо позеленело. Теперь `build_vec` в конце сверяет оверлеи в образе с
собранными .bin и предупреждает; правильный порядок:

```
python3 tools/build_vec.py && python3 tools/data/build_edd.py && python3 tools/build_vec.py
```

## Смена уровня в игре

Скрипт `action_finish_level` ставит `player_dead = 2 + параметр`: 2 — выход в меню, 3 — следующий
уровень (номер он уже увеличил), 4 — игра пройдена. Раньше обрабатывалась только двойка, тройка
просто продолжала текущий уровень. Теперь при тройке набор читается с дискеты заново.

**Загрузчик одноразовый.** В ROM он лежит по $7E00 ПОВЕРХ таблиц `rev256`/`vec_slot_tab`: отрабатывает
при старте и тут же затирается ими. Поэтому копия (512 Б) лежит в наборе (`build_edd.FDDCOPY`,
стр.2 $BD00) и перед загрузкой возвращается на своё место; таблицы после загрузки строятся заново
(`vec_init_rev256`, `vec_slot_init`), затем читаются таблицы уровня и `cls` — VRAM была буфером
загрузки, без очистки по краям поля остаётся мусор.

**Таблица дорожек уровней жила только в образе.** `vfl_dirtab` прошивает `build_fdd` прямо в ROM
внутри образа дискеты, а в `build/ianna.rom` она нулевая — и копия загрузчика в наборе унаследовала
нули. При переходе загрузчик видел «дорожка 0 = набора нет» и выходил, прочитав один сектор. Теперь
таблица сохраняется в ОЗУ при старте, пока цела, и возвращается перед повторной загрузкой.

**Проверка headless.** `run_vec` научился эмулировать ВГ93 (чтение секторов из образа, геометрия
80×2×5×1024) — до этого вся дискетная ветка проверялась только руками в эмуляторе, и зависание
образа мы так и поймали. Заодно выяснилось, что при дискетном прогоне ROM надо брать ИЗ ОБРАЗА
(за дескриптором, со смещения $80), иначе таблица дорожек нулевая.

`tools/fdd_boot_test.py` гоняет пустой квазидиск + образ дискеты: загрузка набора уровня 1 совпадает
с эталоном на 100 %, `--next` дополнительно проверяет переход — читается 70 секторов, в квазидиске
оказывается набор уровня 2 (расходятся только блоки, которые правит рантайм: пул, музыка, песня
уровня), палитра в ОЗУ совпадает с той, что лежит в новом наборе, и уровень 2 рисуется.

## Голем в двух плоскостях (четыре цвета)

Уровень 2 не помещался в квазидиск: восемь банков спрайтов — варвар (два), скелет, орк, тролль,
камень, голем (два) — это 178 КБ, и дело даже не в объёме (по сумме выходило 250 из 256), а во
фрагментации. Тайлы обязаны лежать в стр.0 (страница зашита в блиттере), карта уровня — в стр.1 по
$8000 (её адреса абсолютные), стр.3 изрезана служебными блоками; непрерывных кусков под банки по
23 КБ набиралось пять-шесть из восьми. Полный перебор размещений это подтвердил (жадная укладка
давала ложные отказы, см. tools/kvaz_pack.py).

Резерва в кадрах нет: у скелета, орка, тролля и голема заполнены все 41 кадр, и врагам достижимы
все состояния — они ходят по тем же функциям, что герой (отдельных enemy-состояний в движке нет).
Не подтверждены только приседание (10..12) и комбо (26..27), но их отсутствие проверкой исходников
не доказать — скрипты лежат в двоичных данных уровня. Второй банк героя (29 кадров: прыжки, бег,
торможение, хват) врагам не нужен — у них его нет и в оригинале.

Поэтому голема кладём в ДВЕ плоскости: у него семь красок, но две из них — бежевая и тёмно-серая —
занимают 2.3 % точек. Выбран вариант «А»: белый уходит в голубой, редкие полутона — в тёмно-синий,
остаётся чёрный контур, тёмно-синие тени, синее тело, голубая освещённая сторона.

Формат: 288 байт на кадр вместо 576, строка — три байта [старший бит цвета, маска, младший бит],
поэтому блит читает по ДВЕ строки за три чтения стеком. Прозрачность несёт маска, а не нулевое
значение, так что все четыре значения 0..3 — цвета. Перестановка цветов уровня 2 собирает палитру
так: 0 чёрный, 1 тёмно-синий, 2 синий, 3 голубой.

**Три ловушки:**

1. **Порядок плоскостей.** В формате первым идёт СТАРШИЙ бит цвета (`planes_of_row`: bit = nplanes-1-p),
   а значения 0..3 живут в двух младших битах — значит данные пишутся в третью и четвёртую плоскости
   ($C000/$E000), а первые две спрайт гасит. Сначала я положил наоборот, и голем вышел зелёно-жёлтым.
2. **Пул затирал спрайт.** Двухплоскостной путь идёт мимо пула, а пул выводит свой буфер поверх —
   голем рисовался и тут же пропадал. Тогда в блоке таблиц уровня завели флаг «пул не включать».
   (СНЯТО 2026-09-03: двухплоскостной спрайт рисуется в слот пула, см. «Пул на ВСЕХ уровнях».)
3. Гашение старших плоскостей обязательно: фон уровня их использует, и без него под спрайтом
   остались бы старшие биты фона. Отсюда и выигрыш по скорости невелик — экономятся два `or`.

Сделано и проверено: данные, палитра, признак банка (бит 0 порта в таблице банков), адрес кадра
(n*288 — сдвигом уже посчитанного n*576), прямой блит (150 байт). Голем рисуется правильными
цветами и держится до конца тика; кадр уровня 1 совпадает с эталоном побайтно.

**Не сделано:** зеркальный путь — голем, идущий влево, рисуется неотражённым. Нужно ещё около
150 байт ROM, а свободно 32.

### Разбор резерва мёртвого кода: его нет

Список из 59 «несосланных» меток на 1.9 КБ разобран поштучно, и от него не осталось ничего.

**Первый фильтр — изолированность.** Метка годится в кандидаты, только если перед ней БЕЗУСЛОВНЫЙ
выход (`ret`, `jp метка`, `jp (hl)`). В исходном разборе изолирующим считался любой `jp`, включая
условный, — а перед 54 метками из 59 стоит именно условный переход или обычная инструкция, то есть
код в них ПРОВАЛИВАЕТСЯ сверху и они живые. Осталось 5 меток на 125 байт.

**Второй фильтр — алиасы и оверлеи.** `fillArea` (48 Б) — второе имя для `fillArea_slow` на том же
адресе, по профилю отрабатывает 200 раз за тик. `vec_ovl_call` (25 Б) вызывается из `pause_ovl.asm`,
который собирается отдельно, — в основном образе ссылки нет, поэтому ассемблер честно пишет «unused».
Осталось 3 метки на 52 байта.

**Третий фильтр — вырезание с проверкой кадра.** Вырезал `score_password_string_rom` (20 Б) — кадр
разошёлся с эталоном. Вырезал `entity_script_pointers` (16 Б) — тоже разошёлся. Обе адресуются
косвенно: код берёт адрес соседней метки и идёт по смещению, так что «нет ссылок на имя» ничего не
доказывает. Откатил, кадр снова совпадает.

**Вывод:** свободного кода в образе нет, искать место надо не здесь. Инструмент `strip_dead` оставлен
в build_vec без вызовов — если появится честный кандидат, резать им и обязательно сверять кадр
(`tools/shot_tick.py --fixrand`): косвенная адресация ловится только так.

Значит зеркальный путь двухплоскостного блита (около 150 байт) придётся размещать иначе — например,
собирать отдельным бинарником, как оверлеи меню, класть в набор уровня и копировать при старте
поверх таблицы слотов ($7F00): на уровне с двухплоскостным спрайтом пул всё равно выключен, и
таблица слотов там не нужна.

### Вынос кода из ROM в набор уровня (приём на будущее)

Места в ROM нет, а мёртвого кода в нём не оказалось — значит редкий код надо выносить. Приём тот же,
что у оверлеев меню: собрать отдельным бинарником с импортом символов из листинга, положить в набор
уровня и при старте скопировать в ОЗУ. Точка посадки — ТАБЛИЦА СЛОТОВ ($7F00, 256 Б): на уровне с
двухплоскостным спрайтом пул выключен, слоты там не нужны. Копируем всегда, а `vec_slot_init` на
обычных уровнях тут же перезаписывает это место — проверка не нужна.

Так вынесен зеркальный двухплоскостной блит (190 Б из 256). Прямой остался в ROM.

**Ловушка, стоившая двух заходов:** внутри блита SP подменён на данные спрайта в квазидиске, поэтому
там НЕЛЬЗЯ пользоваться `call`/`ret` — адрес возврата лёг бы прямо в читаемые данные, а `ret` взял
бы оттуда мусор. Первая версия выносила общие куски в подпрограммы и по этой причине не работала;
всё пришлось развернуть в линию.

**Вторая ловушка — почему падал вынесенный блит.** Запрет пула я поставил не в том месте: флаг
`vec_pool_on` не включался, но `vec_pool_begin` всё равно доходил до разметки слотов
(`vpb_rect_assign`), а та ПИШЕТ в таблицу слотов — то есть прямо в код блита, лежащий на $7F00.
Падало не сразу и не всегда: сначала портился первый байт `vec_stk_leave`, потом выполнение
уходило в мусор. Проверка `vec_pool_ban` перенесена в самое начало `vec_pool_begin`.

Состояние: работают оба направления. Голем рисуется верными цветами и на экране, где идёт вправо
(4,6), и там, где влево (5,6); кадр уровня 1 совпадает с эталоном побайтно. Экраны с големом идут
7.5-7.6 тик/с — пул на этом уровне выключен, так что цена видна.

## Палитра по экранам и четырёхцветный скелет

Чтобы четырёхцветный спрайт не перекрашивал фон, слоты палитры 1..3 отданы ему целиком, а фон и
обычные спрайты уведены в слоты 0 и 4..15 (перестановка уровня 2, `COLOR_TARGET_BY_LEVEL`). Тогда
смена этих трёх слотов при загрузке экрана фона не касается вовсе — и копии тайлов не нужны.

Не хватало ровно одного слота: тринадцать цветов на двенадцать мест. **Слит салатовый #91FF00 с
зелёным #00B600** — это блики на коже орка (15 % его точек) и 0.7 % фона; герой и тролль не
затронуты. Слияние применяется НА ВСЕХ УРОВНЯХ, чтобы орк выглядел везде одинаково.

Таблица палитр экранов (три байта на экран) лежит в наборе, читается при `LoadScreen` процедурой в
вынесенном оверлее ($7F03). Тройки: голем — тёмно-синий, синий, голубой; скелет — белый, бежевый,
тёмно-серый; валун — коричневый, тёмно-серый, бежевый.

**Четыре ловушки, все пойманы прогоном:**

1. **Слияние должно идти ПОСЛЕ перестановки.** Сначала я слил цвета до свопов — и на уровне 1
   слитый салатовый уехал в слот, где сидело синее небо: небо позеленело.
2. **Таблица обязана лежать в окне $A000-$DFFF.** Первый адрес ($9F00) оказался ниже окна, чтение

3. **Адрес таблицы у каждого уровня свой** (у первого $C900, у второго $A000: свободное место в окне

4. **Набор четырёхцветных банков тоже зависит от уровня.** Скелет есть и на первом уровне, но там

### Загрузка уровня: где на самом деле время

Чтение потока с дискеты переписано на прямое копирование из буфера сектора (`vfl_stream`): на байт
уходит ~25 тактов вместо ~65, потому что раньше каждый байт шёл через вызов, сохранявший HL и
переписывавший указатель. Заодно тем же кодом читается таблица длин блоков — старая `vfl_byte`
больше не нужна, и загрузчик остался в своих 512 байтах.

Выигрыш оказался скромным — 9.3 → 8.65 млн инструкций (7 %), потому что время не там. Профиль
загрузки набора:

| куда уходит | доля |
|---|---|
| распаковка aPLib (`ap_*`) | 28 % |
| копирование внутри распаковщика (`z_ldir_l`) | 19 % |
| запись в квазидиск стеком (`vfl_push`) | 10 % |
| ожидание данных от контроллера (`vfr_drq`) | 10 % |
| чтение потока (`vfl_st2`) | 8 % |

То есть половина — распаковка. А те тридцать секунд, что видны на стенде, эмуляция вообще не
показывает: она читает секторы мгновенно, а на железе это обороты дискеты и шаги головки. Дальше
ускорять имеет смысл только с замером на стенде — например, проверив, не теряется ли оборот между
соседними секторами.

## ✅ Пул на ВСЕХ уровнях: двухплоскостной спрайт рисуется в слот — 2026-09-03

Владелец посмотрел уровень 2 в Emu80: прямой режим мерцает «страшно сильно» (фон под спрайтом
стирается тайлом, спрайт дорисовывается позже, луч ловит дыру), с пулом — нет. Пул до этого работал
только на уровнях 1, 7 и 9 — там, где нет четырёхцветных врагов. Решение: пул везде.

**Что мешало.** Двухплоскостной кадр (288 Б, строка 3 Б `[плоскость 2, маска, плоскость 3]`) умел
рисоваться только прямо в VRAM, а зеркальный его вариант вообще лежал в наборе уровня ПОВЕРХ таблицы
слотов ($7F00) — места в ROM не было. Одно исключало другое: пока по $7F00 лежит блит, слотов нет.

**Тело строки вместо целого пути.** Пролог сегмента (`dsp_seg`/`dspm_seg`: слот по vec_slot_tab,
адрес, число строк, самомодифицируемый предел), цикл колонок, разбор `vec_spr_cx` и бюджет DI у
четырёх- и двухплоскостного путей ОДИНАКОВЫ — различается только разбор данных строки. Поэтому пролог
кончается самомодифицируемым `jp` (`dsp_go`/`dspm_go`), а `drawSprite_pool` по биту 0 порта банка
подставляет туда `dsp_row`/`dspm_row` или `b2p_row`/`b2pm_row`. Добавилось 272 Б вместо ~600.

**Ловушка — пара строк.** Три байта на строку читаются стеком по два, значит строки идут ПАРАМИ:
тройка `pop` даёт строку A целиком и первый байт строки B. А сегмент пула кончается на границе
супертайла, и его длина может быть нечётной — пара рвётся. Первый байт строки B уезжает в
`vec_b2_carry`, пролог отрабатывает как обычно, и новый сегмент начинается сразу со строки B
(`b2p_split` → `b2p_cont` → `b2p_rowb`). В игре это не срабатывает никогда: спрайты стоят на чётных
строках, `ybot = y + NY - 1` при NY = 32 всегда нечётный, и все сегменты выходят чётной длины —
поэтому ветку пришлось поднимать искусственно (см. ниже). Разрыв пары на границе КОЛОНКИ невозможен:
NY чётное (нечётное разъехалось бы и в прямом блите — там на строку A тратится четыре байта
источника вместо трёх, а хвост колонки считается как (32-NY)*3).

**$7F00 освобождён.** `blit2_ovl.asm` удалён; зеркальный прямой блит (`vec_blit2m`) и процедура
палитры экрана (`vec_scrpal`) переехали в образ, в `src/vec/vec_blit2.asm`. Прямые блиты остались —
они нужны на переполнении пула и на супертайлах без слота (за 60 тиков на ур.6 6,1 это 18 вызовов,
на ур.4 6,2 — 2 зеркальных). `vec_scrpal` сам выходит при `vec_scrpal_addr = 0`, поэтому хук
LoadScreen стал безусловным `call`, а флаг `vec_pool_ban` остался только стендовым (POOL_OFF=1 —
«прямой режим для сравнения»). Место под переезд нашлось так: `vec_main` больше не копирует BLIT2SRC
и всегда зовёт `vec_slot_init`; `vpb_overflow2` зовёт `vec_slot_init` вместо своей копии очистки;
`vec_scrpal` считает номер экрана через `Mul8x8` оригинала. **Зазор ROM 502 → 0 Б** — следующий
резерв это нулевая страница $003B-$00FF (197 Б; проверено прогоном: за 60 тиков туда ноль записей)
и освободившиеся 256 Б в стр.2 набора по $BF00.

**Чем доказано.** `tools/b2pmodel.py` — модель формата на Python против самого блита: на каждом
вызове снимается вход и содержимое пула ДО, считается ожидаемый пул и сверяется побайтно по всем
80 слотам. 0 расхождений на 42..122 блитах в сцене. Ключ `--yodd` (в `poolstat.py` и `b2pmodel.py`)
делает y спрайтов нечётным — и в списке SPDATA до разметки слотов, и в самом вызове блита, иначе
слоты и рисование разъедутся; тогда `b2p_split` срабатывает 114-318 раз за прогон, `b2pm_split` — 30,
и расхождений по-прежнему 0. Плюс `cmpbuild --norand` 60 тиков на восьми сценах (1 4,5; 2 4,6; 2 5,6;

### Голова героя у нижней кромки (23.10)

Жалоба с MiSTer: герой висит на уступе у самого низа поля — головы нет. Причина в `drawSprite`
(`vec_vdp.asm`): начало первой колонки сдвигалось на `vec_spr_skip2` = (32−NY)·3 Б всегда, а для
кадра в четырёх плоскостях строка 6 Б — нужен полный `vec_spr_skip`. Обрезанный спрайт (y+32 > 160,
NY < 32) выводил строки со сдвигом на (32−NY)/2: низ кадра поднимался, верхние строки (голова)
выпадали. Следующие колонки шли по полному пропуску и были верны относительно первой, так что
картинка выглядела цельной, только без верха. При NY = 32 пропуск нулевой — вне кромки дефекта нет.
Стенд воспроизвёл (кадр висения, банк 3, кадр 3, y = 140); после правки виден верх кадра. +9 Б кода.
